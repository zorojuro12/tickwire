## Decisions Made

- **The aim-vector format amendment** — see the "Decided" line above and the plan's Task 3.
- **P2 takes the full scope: server + headless load client + raylib renderer.** The design doc's P2 row calls it "first demoable thing" and the workflow guide's import map reads it as "authoritative server, raylib client, first demo". The headless client is needed for P5's benchmark regardless, so building it now costs nothing later.
- **`World` gets movement *and* hitscan at P2**, the full resolution-doc § Q2 surface. P6 then adds only the rewind, which makes the lag-comp toggle a before/after rather than a new feature.
- **Spec-driven inline plan format again, not code-driven/delegated.** `delegating-plan-tasks` is installed and would want pre-written code, but P1's journal records that the inline RED/GREEN cycle caught real defects at nearly every checkpoint, and P2 is where simulation semantics get decided.
- **Hit counts stay server-side, off the wire.** `PlayerState` is frozen at 24 bytes with no room for health or score, and the format is being reopened once this phase, not twice. P6 can add a hit-feedback `MsgType` additively (values 6–255 are unused) without touching the header or the version.
- **Task ordering puts the one environment-risk task last.** Tasks 1–8 are a complete, shippable, headless phase on their own; Task 9 (raylib) can fail without costing anything else, and the plan says explicitly to stop and record rather than improvise around it.

## What Worked

- **Checking the environment before writing the plan, rather than planning around an assumption.** Three checks paid for themselves: Docker is up and the pinned image is present; the container has `libX11` but is **missing** `libGL`, `libXrandr`, `libXi`, `libXcursor`, `libXinerama` and the GL headers (so the plan's Task 9 carries the exact `apt-get` line rather than "add raylib's deps"); and WSLg is live on the host (`DISPLAY=:0`, `/tmp/.X11-unix/X0` present), so the deferred display question is a plausible spike rather than a wall.
- **Reading `scripts/tw` before writing a task that edits the `Dockerfile`.** It short-circuits on `docker image inspect "$IMAGE"`, so editing the Dockerfile without bumping the tag silently reuses the stale image and the change appears not to work. That's now a Global Constraint in the plan and a one-commit requirement in Task 9, instead of a lost hour during execution.

## What Didn't Work

Nothing was tried and abandoned — this was a read-and-plan session with no code written. Recording the near-miss instead, since it would have been a genuine dead end: the resolution doc's § Q2 `World` surface lists `resolveHitscan(shooter, aim_x, aim_y)` while P1's frozen `InputCommand` carries no aim field, so the two specs cannot both be satisfied as written. It was caught by cross-reading the two documents against each other before planning, not by either document flagging it.

## Open Questions / Blockers

- **The raylib display path is unproven.** The deps are missing from the image and WSLg passthrough into a container is plausible but untested. If Task 9 Checkpoint 2 fails, the plan says to record the exact failure (and which of the three layers failed — raylib's build, the X connection, or GLFW's window creation) in `docs/project-history.md` and stop. The documented fallback — building the renderer on the host — needs a `g++-10` install that requires a password no automated session has, so it is the user's decision, not a workaround to improvise.
- **Task 6 (`Server<T>`) is the largest task in the plan** — four checkpoints over a template class touching the world, the sessions and the ring. Not split, because each checkpoint is a genuine RED at the same public surface and splitting it would mean shipping a server that accepts joins but drops inputs. The plan names the boundary after Checkpoint 2 as a defensible place to pause if it runs long.
