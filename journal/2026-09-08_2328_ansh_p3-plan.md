## Decisions Made

- **P2's apply-on-arrival input handling is incompatible with reconciliation
  and had to become a tick-matched `InputBuffer`.** The client's replay assumes
  "N pending inputs = N simulated steps," but P2's server latches whatever input
  arrives and lets `World::step()` integrate it for however many ticks pass
  until the next packet — a count that depends on network jitter and that the
  client cannot know. Under the exact 200ms-latency condition the demo exists
  to showcase, this would show up as visible per-snapshot correction stutter.
  The user was given the tradeoffs explicitly (buffer = correct but touches
  ~6-8 shipped, green P2 server tests; apply-on-arrival = zero churn but
  reconciliation fights itself under jitter) and chose the buffer.
- **The wire format needs no amendment — verified three ways, not assumed.**
  Reconciliation needs "which inputs has the server consumed": a snapshot's
  existing `tick` field already answers this, because Task 3 makes the server
  consume inputs strictly in tick order. Clock sync needs a feedback signal:
  `ack_tick − tick` on a snapshot is the session's server-side input-buffer
  depth — the entire clock controller runs off this without ever measuring RTT
  as a round trip. RTT for the HUD needs an echo: `ack_tick` names an input the
  client still holds a send time for, so RTT is a subtraction, not a new field.
  Three needs, zero new fields — this is the payoff of P1 reserving
  `tick`/`send_time_ms`/`ack_tick` specifically so P3 wouldn't have to reopen
  the frozen format.
- **The client predicts the local player only**, never remote players.
  Predicting a remote player would require predicting *its* inputs, which
  nothing can do; smoothing remote players between snapshots is entity
  interpolation, explicitly P4's scope. `Client`'s prediction world holds
  exactly one player.
- **Fires resolve in a second pass, after every session's input for the tick
  has been applied.** A single fused apply-and-fire pass would make hit
  detection depend on session iteration order (shooter's fire resolving against
  a target's stale pre-input position). P2 had this ambiguity implicitly;
  making the two passes explicit removes it. Plan Task 3 Checkpoint 3 pins this
  with a test that may pass on first write if Checkpoint 1 was implemented as
  two passes to begin with — the plan explicitly permits that outcome and says
  not to force a failure.
- **`sim::World::latched_` is dead state** — written by `addPlayer` and
  `applyInput`, never read (`step()` integrates `players_[i].vx/vy` directly).
  Recorded as a `/refactor-clean` candidate, deliberately not deleted this
  phase. This finding is *why* Task 1's `setPlayerState` (position + velocity
  only) is sufficient for reconciliation — there's no hidden latch state also
  needing to be restored.
- **Measurement stays "track and print," not a benchmark harness.** The user
  wanted the tradeoffs explained in plain terms rather than abstractly listed;
  the answer given was that a sweep-driven percentile table is P5's job (the
  design doc puts the headline numbers table there), and building a mini
  version of it inside P3 — the phase the design doc already calls the riskiest
  — was the wrong order. `PredictionStats` (p50/p99/worst over a rolling
  window) costs ~80 lines, is a straight subtraction the client already
  computes at reconciliation time, and gets printed by `tw_loadclient` at exit
  with no CSV or sweep driver. P5 inherits the instrumentation if it's later
  worth promoting.
- **GUI wired in P3, not deferred to P4.** The toggle is nearly free once
  prediction exists (~30 lines: a bool skipping replay, rendering the snapshot
  position instead) and prediction/interpolation touch different code paths
  (local player vs. remote players) so there's low collision risk in touching
  the renderer twice. Kept as the phase's last task, mirroring P2's own
  placement of its one unverifiable risk (the raylib display path) last.

## What Worked

- Reading the actual `Client<T>`/`Server<T>`/`World` code before scoping
  questions were framed caught a real design flaw (the apply-on-arrival
  incompatibility) before it became a mid-execution discovery — the same
  failure mode P2's planning session caught between the resolution doc and the
  frozen `InputCommand` wire layout.
- Verifying "does the wire format need to reopen" against the actual header
  fields, rather than assuming P1's reservations were sufficient, turned up a
  genuinely elegant answer (`ack_tick − tick` as the clock-sync signal) that
  wasn't obvious from the references alone — it fell out of reading `session.h`
  and `server.h`'s existing `touch()`/`lastInputTick()` contract closely.
